优先级 新增 / 调整项 为什么重要 对应的 Codex 式模式
P0 新增专门的 finance router skill，比如 `finclaw-index` 它负责把请求分流到 intake、结账分析、差异分析、正式报告、dashboard、情景模拟、审计复核或追问答疑等路径；下游主工作流默认落到 `traceable-financial-analysis`，而不是直接改写 `finclaw-report-analysis`。 采用 `index` router 与 worker skill 分离模式；`traceable-financial-analysis` 作为主要 worker contract。
P0 新增 `finclaw-user-context` 存公司画像、主体结构、会计科目口径、数据源优先级、历史报告风格、常用 KPI、默认期间口径和访问准备状态；每次分析前先做 preflight，决定是直接进入 `traceable-financial-analysis`，还是先补文件 / 补权限 / 补上下文。 采用 `user-context` 的 preflight + saved context 模式，但领域内容改成财务专用。
P1 拆开 business contract 和 execution contract 这一步不去改 `finclaw-report-analysis`。改造方式是把 `traceable-financial-analysis` 提升为新的主 contract：它拥有产品语义、审计要求和报告边界；执行细节再继续下沉到 `maybeai-formula-report`、`maybeai-sheet` 和后续 worker skill。 采用 router skill + focused skill body 分层；旧 `finclaw-report-analysis` 保持兼容，不纳入本轮重构。
P1 按分析任务类型增加 finance-focused worker skill 比如：`variance-analysis`、`cash-flow-diagnostics`、`working-capital-review`、`consolidation-review`、`budget-vs-actual`、`scenario-planning`。 `metric-diagnostics`、`kpi-reporting`、`product-business-analysis` 这种专项化模式

8. `finclaw-index` 与 `finclaw-user-context` 设计细化

下面这部分可以直接当成后续拆 skill 的设计草案。目标不是让它们“什么都做”，而是让它们只做自己的控制面职责，然后把主分析流程稳定交给 `traceable-financial-analysis`。

Skill 输入 核心职责 不该承担的职责 标准输出
`finclaw-index` 用户请求、附件/路径信息、用户上下文摘要、当前可用能力状态 识别意图；判定属于 intake、结账分析、差异分析、正式报告、dashboard、情景模拟、审计复核还是 Q&A；选择主 skill；决定是否先走 preflight 或 data validation；拼出 route plan。 不直接写 workbook，不直接生成财务结论，不直接做底层解析或公式写入。 结构化路由结果：`request_type`、`needs_preflight`、`primary_skill`、`supporting_skills`、`blocking_gaps`、`delivery_mode`。
`finclaw-user-context` 用户身份或会话信息、已有公司记录、源配置记录、历史交付偏好、当前请求 做 preflight；读取和更新公司画像、主体结构、会计科目口径、常用 KPI、默认模板、默认时间粒度、数据源优先级、权限准备状态；告诉 router 当前能否直接开跑。 不替代业务分析，不负责产出正式报告，不承载图表渲染和 workbook 操作。 结构化上下文结果：`context_summary`、`source_readiness`、`preferred_templates`、`default_entity_scope`、`known_metric_defs`、`missing_requirements`。
模块 建议子能力 决策点 与 `traceable-financial-analysis` 的关系
`finclaw-index` `intent-classifier`、`route-planner`、`capability-gate`、`delivery-mode-selector` 现在是先补文件、先补权限、先补上下文，还是已经可以进入主分析流程。 它不做分析，只负责把请求稳定送到 `traceable-financial-analysis` 或相关 worker skill。
`finclaw-user-context` `company-profile`、`source-registry`、`metric-memory`、`template-preference`、`readiness-check` 当前公司是谁、用哪套口径、哪些源是可信源、哪些模板是默认模板、当前是否缺关键输入。 它为 `traceable-financial-analysis` 提供上下文地基，避免每次都从零开始问和猜。
最小运行链路 说明
1. 用户提问 → `finclaw-index` 先判断任务类型，以及是不是财务正式工作流请求。
2. `finclaw-index` → `finclaw-user-context` 拿公司、实体范围、默认模板、可信数据源和 readiness 状态。
3. 若缺关键输入 → 停在 preflight 比如缺报表、缺权限、缺期间范围、缺实体选择，此时先补信息，不进入主分析。
4. 若上下文齐备 → `traceable-financial-analysis` 进入主 contract skill，开始财务业务语义、审计规则和报告边界控制。
5. 再下沉到执行层 需要 workbook / 公式链路时，调用 `maybeai-sheet`、`maybeai-formula-report`、`finclaw-validate-data` 和后续 worker skill。
6. 最终回到 delivery 层 根据 router 选定的 delivery mode 输出 MaybeAI workbook、HTML、PPT、audit pack 等产物。

9. 实操建议

针对你的业务上下文，我不建议 1:1 照抄 Codex 参考结构。它在平台治理上更成熟，但本质上是通用型。你的优势在于，你已经掌握了 finance workflow、audit 语言、boss-review 结构，以及 workbook lineage 模型。

更合理的路线是：保留你的金融专用核心，然后在外层补上 Codex 风格的 control plane：

  • 保留 `maybeai-sheet-skill` 和 `maybeai-formula-report` 作为稳定执行层。
  • 明确采用 `traceable-financial-analysis` 作为后续增强和分层改造的主 contract skill。
  • 保持 `finclaw-report-analysis` 不动，继续作为兼容层和历史契约存在，不在 `~/work/ai/maybeai-uni/skillhub` 里直接重构它。
  • 补一个真正的 router、一个真正的 user-context/preflight skill、一个真正的 validation skill，以及按任务拆分的 finance worker skill，并统一挂到 `traceable-financial-analysis` 这条主线上。
  • 把 simulation、dashboard、delivery 变体做成一等 skill，而不是塞在一个大 contract 文件里的附属说明。

这样改完之后，你的框架会同时变得 更稳、更像 Codex，同时在真实会计和财务运营场景里仍然会比通用 analytics 系统更强。
